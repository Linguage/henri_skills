# 项目与技术复盘

## 识别

当文章主要依靠项目记录、日志、提交、错误现象、技术决策和结果成立时使用本规则。目标是解释问题为何发生、如何判断以及哪些认识能够复用；展示工作量不构成主要目标。

## 硬约束

- 不虚构日志、报错、提交、指标、时间线或验证结果。
- 区分直接触发点与更深的系统条件，不把最后一次操作自动写成唯一根因。
- 区分当时掌握的信息与现在回看的理解。
- 说明人的实际操作，但把改进指向系统、流程、工具和信息条件；无责不等于无人负责。
- 行动项必须有可验证的完成状态；“加强意识”“以后谨慎”不算行动项。

## 推荐推进

按需要选择：原始目标 → 实际影响 → 关键时间线 → 触发因素与促成条件 → 处理和证据 → 结果 → 遗留问题。

- 用日志、提交、报错、截图、指标或可复现步骤承担技术判断。
- 解释当事人在当时信息下为何作出该决定，避免事后羞辱。
- 面向博客读者压缩内部台账，只保留会改变判断的细节。
- 结尾说明改进后来是否得到验证；尚未验证就明确写出。

## 审查问题

- 读者能否复原最关键的决策链，而不必读完整工作日志？
- 文章是否把相关性误写成因果，或在没有证据时宣布根因？
- 每段过程是否增加了新决策、新证据或新认识？
- 结论是否能指回正文中的具体事件？

## 常见偏移

- 按日期或提交逐项罗列工作。
- 每节末尾自动生成一条通用工程道理。
- 把工具或 AI 写成抽象主角，却不说明它具体做了什么。
- 只写修好了什么，不写如何确认已经修好。
